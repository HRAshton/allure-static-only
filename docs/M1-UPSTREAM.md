# M1 upstream feasibility spike

Status: **draft / UNVERIFIED in browser**, not an accepted milestone.

## Pinned upstream

- Repository: https://github.com/allure-framework/allure3
- Commit: `b26b092cc16c69a5fb74ea0d68e565d35a470ef4` (2026-10-22)
- Frontend workspace: `@allurereport/web-awesome`
- Frontend build: `packages/web-awesome/dist/multi`, generated by Webpack
- Loader: `packages/web-commons/src/data.ts`
- Upstream package manager: Yarn 4.18.1
- Attribution: Apache-2.0; include upstream licenses and NOTICE in release artifact

Upstream's `loadReportData` reads **base64 strings** from `globalThis.allureReportData` when `globalThis.allureReportDataReady` is set. The JSON fetch helper then uses `data:` URLs for those bytes. This appears to make a code patch unnecessary for the first integration.

## M1 implementation hypothesis

1. Build the pinned **real** Allure Awesome UI at build time (Node/Yarn allowed).
2. Copy the generated `dist/multi` assets and inject a small independent import overlay.
3. Hold `allureReportDataReady = false` until the user selects a generated Awesome report directory.
4. Map `widgets/**` and `data/**` files to base64 strings via browser File APIs.
5. Set the globals to allow the upstream UI to fetch from memory. No report bytes are sent to a backend.

The M1 importer intentionally accepts **already generated Awesome report files**, not raw test results. M3 implements raw `allure-results` conversion; this separation proves the risky UI boundary before implementing parsers.

## Required browser checks

- The upstream HTML/JS/CSS loads without a runtime API.
- Loading a generated fixture shows an actual test in the real Allure UI.
- The browser network panel shows only static asset requests and no result uploads.
- Broken/missing paths report errors, do not escape the origin or execute test scripts.
- A clean build at the pinned upstream SHA is repeatable.
- Keep dependency provenance; adjust the bootstrap when the upstream data interface changes.

This spike is a **hypothesis and useful starting code**, not proof of a working report viewer.

## Limited CI

Only M1 branch pushes (and deliberate manual dispatches) run the one-job, 20-minute-cap workflow. It does not trigger on every PR or future milestone branch. Its browser check uses a locally generated Allure fixture and fails if any third-party HTTP request is made by the injected shell. This is build-time verification only, not a production backend.

## Browser integration finding

A browser smoke test confirmed that the importer places the generated Awesome data into the upstream globals. The upstream UI must also receive a populated `allureReportOptions` object compatible with the options produced by the official Awesome report generator. In particular, a missing `createdAt` caused an `Invalid time value` runtime exception and an empty root DOM. M1's static bootstrap now provides a valid timestamp and stable version/identity fields. This does not close M1 until the end-to-end browser smoke test passes.
